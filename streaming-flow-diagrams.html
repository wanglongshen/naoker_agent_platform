阶段 2 为什么需要"再查一次"？
在 subscribe() 和初始 replay 之间存在 毫秒级竞争窗口：
• 线程 A (SSE 生成器): 刚完成 replay → 准备 subscribe →
• 线程 B (Worker): 在此刻插入新事件 seq=100 →
• 线程 A: subscribe 完成 → 队列里不会收到 seq=100
→ 再查一次 DB 填补这个窗口，确保零丢失。

4.3 SSE 帧格式与编码

# agent_stream.py:49-54 def _encode_sse_event(event) -> str | None: try: # Pydantic 验证 + 序列化 payload = AgentRunEventResponse.model_validate(event).model_dump(mode="json") except ValidationError: return None # 无效事件静默跳过 (EventNotify 也会走到这里被跳过) return f"id: {payload['seq']}\nevent: {payload['event_type']}\ndata: {json.dumps(payload)}\n\n"

实际输出的 SSE 帧：

id: 42 event: answer_delta data: {"id":"evt-xxx","run_id":"run-yyy","seq":42,"event_type":"answer_delta","payload":{"stream_id":"ans-zzz","offset":0,"delta":"量子计算"},"created_at":"2026-07-30T10:00:00Z"}

SSE 协议约定：id: 行用于 Last-Event-ID 重连；event: 行用于 EventSource.addEventListener(type)；data: 行是 JSON 载荷；双换行 \n\n 表示帧结束。

5. PostgreSQL LISTEN/NOTIFY 链路逐行

5.1 发送端：loop.py → repo → pg_notify

# agent_repository.py:225-260 async def append_event(self, run, attempt, event_type, payload, notify=False): # ① 插入事件行 result = await self.session.execute( insert(AgentRunEvent).values( run_id=run.id, ... seq=agent_run_events_seq.next_value(), ).returning(AgentRunEvent) ) event = result.scalar_one() await self.session.flush() if notify: # ② 同事务内发送 PG 通知 (COMMIT 时触发) await self._notify_run_event(run.id, event.seq) return event async def _notify_run_event(self, run_id, seq): payload = json.dumps({"run_id": str(run_id), "seq": seq}) await self.session.execute( func.pg_notify("agent_run_events", payload) )
为什么 notify 放在 append_event 里面，而不是外面？
保证 INSERT 和 NOTIFY 在同一个数据库事务中。PG 的 NOTIFY 只有在事务 COMMIT 时才真正发送。 如果不在同一事务，可能出现"通知发了但事件其实没写进去"的脏通知。

5.2 接收端：postgres_event_listener.py

# postgres_event_listener.py (核心逻辑) async def _listen_loop(dsn, channel, stop_event): while not stop_event.is_set(): conn = await asyncpg.connect(dsn=dsn) # 直连 PG (绕过 SQLAlchemy) await conn.execute(f"LISTEN {channel}") # 订阅 agent_run_events 频道 notification_queue = asyncio.Queue() # 回调安全队列 def _handler(connection, pid, channel_name, payload): notification_queue.put_nowait(payload) # 回调中放入，不堵塞 PG 连接 await conn.add_listener(channel, _handler) while not stop_event.is_set(): payload = await asyncio.wait_for( notification_queue.get(), timeout=1.0 ) event = parse_notification_payload(payload) # → EventNotify(run_id, seq) if event is not None: await event_bus.publish(event) # 投递到 API 进程的 EventBus def parse_notification_payload(raw) -> EventNotify | None: payload = json.loads(raw) run_id = uuid.UUID(payload["run_id"]) seq = payload["seq"] return EventNotify(run_id=run_id, seq=seq) # ↑ 只传 run_id + seq，不传事件体（保持轻量）
为什么 NOTIFY 载荷只传 {run_id, seq}，不传完整事件？
• PG NOTIFY 载荷上限约 8000 字节。搜索结果等大型事件可能超限。
• 事件表是唯一权威数据源——无论通知丢不丢，数据永远在 DB 里。
• 把 run_id + seq 作为"敲门信号"，SSE 生成器收到后去 DB 查完整事件。这样无论通知有多轻量，都不会损失数据保真度。

6. 事件生产端 — Worker 如何输出

6.1 _stream_final_answer() — LLM 流式文字 → answer_delta 事件

# loop.py:626-670 async def _stream_final_answer(self, repo, ctx, messages): stream_id = f"answer-{ctx.run.id}" await self._persist_and_notify( repo, ctx, "answer_started", {"stream_id": stream_id}) answer = "" checkpointed_offset = 0 last_checkpoint_time = time.monotonic() async for chunk in self.llm_client.stream_text(messages): if not chunk: continue # ② _persist_and_notify 内部会: INSERT + pg_notify + publish offset = len(answer) answer += chunk await self._persist_and_notify( repo, ctx, "answer_delta", {"stream_id": stream_id, "offset": offset, "delta": chunk}) # ③ checkpoint: 每 256 字符或 0.4s 存一次完整文本快照 uncheckpointed = len(answer) - checkpointed_offset elapsed = time.monotonic() - last_checkpoint_time if uncheckpointed >= 256 or elapsed >= 0.4: await self._persist_and_notify( repo, ctx, "answer_checkpoint", {"stream_id": stream_id, "text": answer, "offset": len(answer)}) checkpointed_offset = len(answer) except Exception as exc: await self._persist_and_notify( repo, ctx, "answer_failed", {"error": str(exc), "offset": len(answer)}) raise await self._persist_and_notify( repo, ctx, "answer_completed", {"stream_id": stream_id, "text": answer, "length": len(answer)}) return answer
Offset 校验：每个 delta 标注"从第几个字符开始追加"。前端验证 offset == answerText.length，不匹配则触发重连。
Checkpoint 点：每 256 字符或 0.4 秒存完整文本快照。即使前面的 delta 丢失，checkpoint 能完整恢复。

10. 还能怎么优化？

10.1 优化空间总览

#优化点当前优化后收益难度
1NOTIFY 载荷扩增只传 {run_id, seq}加 event_type + 小 payload省一次 DB 查回低
2event_bus 类型统一EventNotify + EventItem 双类型统一为 EventItemSSE 循环少一条分支低
3answer_delta 批量写入每 chunk 一次 INSERT + COMMIT攒 50ms 一批写入DB 事务数减少 80%中
4append_event 跳过 flushINSERT RETURNING 后调 flush去掉 flush，等 COMMIT每事件省一次 DB 往返低
5Redis Pub/Sub 替代 PG NOTIFYPG NOTIFYRedis PUBLISH / SUBSCRIBE延迟更低，不占 DB 连接高
6多 Worker 负载均衡单 Worker多 Worker + 租约竞争并发吞吐量提升高

优先级建议：1→2→4→3→5→6。前面 4 个改动量小、收益明确，5 和 6 需要引入新组件和架构变更。

10.2 优化 1：NOTIFY 载荷扩增 — 省掉一次 DB 查询

# 当前：只传信号，SSE 收到后必须查 DB payload = json.dumps({"run_id": str(run_id), "seq": seq}) ↓ SSE 收到 → EventNotify → needs_catchup → SELECT FROM DB # 优化：对于短事件（< 8000 字节），直接携带内容 payload = json.dumps({ "run_id": str(run_id), "seq": seq, "event_type": event_type, # 新增 "payload": payload, # 新增 (answer_delta 通常只有几字节) }) ↓ SSE 收到 → EventItem (完整) → 直接 _encode_sse_event → 跳过 DB 查询!
适用条件：answer_delta 的 payload 通常只有 1-3 字节（一个字）。8000 字节上限绰绰有余。但搜索结果、checkpoint 全量文本等大型事件仍需走 DB 查回。
性能模型：假设每秒 100 个 delta 事件，95% 为小事件（可直接带载荷），节省 95 次 DB SELECT/秒。
端到端延迟降低 ~0.5ms。

10.3 优化 2：event_bus 类型统一 — 简化循环分支

# 当前 SSE 循环：两个分支 if isinstance(item, EventNotify): # ← 只有 {run_id, seq}，不能直接发射 needs_catchup = True # ← 标记"去 DB 查" elif isinstance(item, EventItem): # ← 完整事件，可直接发射 _encode_sse_event(item) → 发射 # 优化后：统一为 EventItem _encode_sse_event(item) → 发射 # ← 一条路径，无论来源
怎么做：改 postgres_event_listener.py 的 parse 函数，构造一个包含 event_type 和 payload 的 EventItem（从 NOTIFY 载荷中提取，如果带了的话）。对于大型事件（NOTIFY 载荷里没带），fallback 到 DB 查询。这样主循环只需一条分支。

10.4 优化 3：answer_delta 批量写入 — 减少事务数 80%

# 当前：每个 chunk 写一次 DB async for chunk in llm_client.stream_text(messages): answer += chunk await _persist_and_notify(repo, ctx, "answer_delta", ...) # ← INSERT + COMMIT # 优化：攒 50ms 的 chunk，一批 INSERT async for chunk in llm_client.stream_text(messages): answer += chunk pending_deltas.append(chunk) # ← 压入暂存区 if time.monotonic() - last_flush >= 0.05: # ← 每 50ms 一批 await _batch_insert(repo, ctx, pending_deltas) # ← 一条 INSERT 多行 pending_deltas = []
LLM 每秒产出 ~100 个 chunk → 当前每秒 100 次 DB 事务。
50ms 批处理后 → 每秒 ~20 次 DB 事务。
事务数减少 80%，DB 连接压力陡降。
权衡：如果进程在两次批次之间崩溃，最多丢失 50ms 的 delta（约 5-10 个 chunk）。已有 checkpoint (256字/0.4s) 兜底，可恢复数据。

10.5 优化 4：去掉 append_event 里的 flush — 再省一次 DB 往返

# 当前 agent_repository.py:225-244 result = await self.session.execute( insert(AgentRunEvent).values(...).returning(AgentRunEvent) ) event = result.scalar_one() await self.session.flush() # ← 这条 flush 是多余的！ # INSERT RETURNING 已经把数据发给 DB 了 # flush 只做了一次 DB 空往返 # 优化后：去掉 flush result = await self.session.execute( insert(AgentRunEvent).values(...).returning(AgentRunEvent) ) event = result.scalar_one() # ← 完成！ # INSERT RETURNING 本身就是一次 DB 交互，不需要额外 flush
每 100 个 delta 事件省 100 次 DB 往返。配合批量写入（优化 3），总体 DB 交互量从 200 次/秒 降到 ~20 次/秒。
