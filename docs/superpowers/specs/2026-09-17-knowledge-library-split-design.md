# 知识库多库拆分设计（行业知识库 → 8 个专业库）

- 日期：2026-09-17
- 状态：设计已获批（用户逐节确认）
- 上游设计：`docs/superpowers/specs/2026-09-17-knowledge-base-management-design.md`（知识库管理两级结构，已实现）
- 相关计划：`docs/superpowers/plans/2026-09-17-knowledge-base-management.md`（已执行）

## 1. 背景与目标

「知识库管理」上线后，全部行业素材都装在**一个**库（行业知识库：192 篇 / 1,501 块）里。一个库太笼统：

- 检索时规则条文、投放手册、行业案例混在一起，噪声大；
- Agent 侧无法"按问题选库"（问合规和问出价命中的是同一池子）；
- 库列表页只有 1 张卡，看不出素材结构。

目标：把行业素材按**性质 + 主题**拆成 8 个专业库，让检索可聚焦、Agent 可按库提问，且拆分过程可审计、可回退。

## 2. 决策记录（用户已确认）

| 决策点 | 结论 |
| --- | --- |
| 拆分维度 | 两层：先分性质（规则 / 其他），方法论再按主题分 |
| 入库范围 | 全量 601 篇（不只已入库的 192 篇） |
| 旧默认库处置 | 8 个库**全部新建**，迁移完成后**删除**老库「行业知识库」 |
| 归类方式 | 规则驱动（官方标签优先 → 标题关键词 → 兜底），不手工逐篇指定 |

## 3. 素材真实体量（实测，2026-09-17）

重要更正：采集清单里的 `char_count` 是**原始文件字符数**（含 JSON 结构、图片引用），不是正文。用真实解析器跑完 601 篇后的实测：

| 性质 | 篇数 | 原始字符 | 真实正文 | 约块数（512 字/块） |
| --- | --- | --- | --- | --- |
| 方法论·白皮书 | 226 | 6,302,285 | 406,080 | ~790 |
| 规则·协议·公示 | 254 | 9,466,615 | 1,276,956 | ~2,490 |
| 其他（课程/案例） | 121 | 3,131,617 | 233,769 | ~460 |
| **合计** | **601** | **18,900,517** | **1,916,805** | **~3,743** |

已入库 192 篇 = 398,081 字 / 1,501 块，与「方法论 226 篇正文 406,080 字」吻合 —— **当前库没有丢内容**。

## 5. 归类规则（唯一事实源）

实现于 `backend/app/services/rag/library_routing.py`，纯函数 `route_library(item) -> (library, matched_rule)`，规则表以常量数据形式与代码同文件维护。优先级从高到低：

1. **规则类素材**（沿用现有 `classify_manifest_item()` 的判定：标题命中 `细则|标准|公示|通知|协议|规则|公告|规范|说明` 且不命中方法论关键词）→ **平台规则**
2. **行业案例**：官方标签命中 `案例-(生鲜|个护家清|食品饮料|珠宝文玩|智能家居|美妆|品牌商家|营销案例)|优秀案例` → **行业案例**
3. 官方标签依次匹配：千川投放 → 直播运营 → 短视频与内容 → 商城与商品卡 → 达人与大促
   - 千川投放：`商品推广(千川)|流量获取|搜索运营|热点搜索优化`
   - 直播运营：`案例-直播运营|直播间运营`
   - 短视频与内容：`案例-短视频运营|短视频运营|AIGC素材|人设打造`
   - 商城与商品卡：`店铺运营|商品优化|商城运营|案例-商城运营|货品运营|抖店运营`
   - 达人与大促：`案例-大促活动|案例-达人合作|达人合作|达人|消费者运营`
4. 标签未命中时，用**标题关键词**按同样顺序匹配（千川|投放|出价|竞价|全域|流量|搜索|推广 → 直播 → 短视频|图文|内容|素材|种草|拍摄|剪辑|人设 → 商城|商品卡|店铺|商品|橱窗|货架|抖店 → 达人|联盟|团长|大促|活动|会员|消费者）
5. 都不命中 → **课程与通用**

同一份规则同时用于：老数据迁移、新素材导入、审计报告生成。

## 6. 执行机制

### 6.1 归类器

新增 `backend/app/services/rag/library_routing.py`：

- 8 个库的定义（slug、名称、描述、kind、匹配模式）为常量表；
- `route_library(item) -> (slug, matched_rule)`；
- `LIBRARY_SEEDS`：8 个库的固定 UUID（幂等插入用）。

### 6.2 一次原子迁移

新增一个 alembic 迁移，按顺序执行：

1. 插入 8 个库（固定 UUID，`ON CONFLICT DO NOTHING` 语义）；
2. 按归类器重算现有全部文档的 `library_id`（**只改归属**：不动 `rag_chunks`、不重算 embedding、不重新切块）。路由所需的官方标签来自采集清单：按**标题**在 `var/kb_industry/manifest/manifest.json` 中查回素材（实测 192/192 篇标题全部可匹配）；
3. 断言老库（`6f1d2c3a-1111-4a2b-9c3d-000000000001`）已无文档引用，否则整笔回滚；
4. 删除老库行。

`downgrade`：重建老库行 + 把全部文档 `library_id` 指回老库（可逆）。

### 6.3 导入其余 409 篇

新增 CLI：`python -m app.scripts.rag_split_import --scope all`

- 逐篇 `route_library` → 在目标库创建 `pending` 文档 → 交给 `rag-ingest-worker` 解析/切分/向量化；
- 幂等：按 `sha256` 跳过已存在文档，重复执行安全；
- 进度在「知识库管理 → 库详情 → 数据集」可见。

### 6.4 清理默认库常量

全仓 grep `DEFAULT_LIBRARY_ID`：若存在"未指定库时的兜底默认库"逻辑，改为指向「课程与通用」的固定 id；若仅是迁移期锚点，直接删除常量。

### 6.5 检索侧

- `POST /api/rag/search`：不带 `library_id` = 跨全部启用库检索（**行为不变**）；带则单库过滤（已有能力）。
- DSH `knowledge_search` 工具：描述中列出 8 个库的名字与用途，新增可选参数 `library`，让模型按问题选库。
- 技能模板 `knowledge-search/SKILL.md` 同步"什么问题上哪个库"。

### 6.6 前端

两级页面已具备，无需新页面。仅补：

- 类型标签映射：行业（7 个库）/ 平台规则（1 个库）；
- 库卡片按篇数降序排列。

### 6.7 审计报告

生成 `docs/rag-eval/library-assignment.md`：601 行「篇名 → 库 → 命中规则」，供人工逐篇核对。

## 7. 边界与非目标（v1 不做）

- UI 手动改单篇文档归属（改归属 = 改规则表后重算）；
- 库级 embedding / 切分参数（8 库共用 512/64）；
- 默认排除规则库、按意图自动选库（等评测触发再上）；
- 新增采集源（素材仍为抖音电商官方单一来源）。

## 8. 风险

**平台规则库占 2,480 / 3,719 块（67%）**，默认全库检索时规则类长文可能稀释方法论问题的命中。v1 保持全库检索不变；若二期评测集 recall@5 掉出 90%，启用"默认排除规则库"或"按问题意图选库"。

## 9. 测试与验收

### 测试计划

| 层 | 用例 |
| --- | --- |
| 归类器单测 | 规则优先级（多标签案例文档归行业案例）、无标签兜底、规则类优先于标签、8 个库均可被命中 |
| 迁移测试 | 迁移后 8 库存在、老库已删、192 篇全部有合法归属、无孤儿文档；downgrade 后老库回来、文档指回 |
| CLI 幂等 | 连跑两次导入，第二次 0 新增（sha256 去重生效） |
| 检索 | 带 `library_id` 只返回该库；不带时结果集与拆分前一致 |
| 报告 | 601 行齐全，每行含"命中规则"列 |

### 验收线

1. 「知识库管理」显示 8 张库卡片，篇数与本文第 4 节实测表一致；
2. 老库「行业知识库」已删除，且无孤儿文档（SQL 断言）；
3. 按库过滤检索可命中：搜「千川出价」命中千川投放库、搜「准入细则」命中平台规则库；
4. 409 篇导入完成、0 失败；
5. DSH 工作台问"平台规则对 XX 的要求"能命中平台规则库并带来源；
6. `docs/rag-eval/library-assignment.md` 落盘，人工抽 10 篇核对无误。
